# Тренажёр проводников ВСМ

Геймифицированный тренажёр нештатных ситуаций на борту высокоскоростного поезда.
Проводник не отвечает на тест с одним правильным вариантом — он ведёт ситуацию:
успокаивает конфликт, решает вопрос по регламенту, укладывается в таймер. Каждое
решение сразу двигает **две шкалы в разные стороны**:

- **лояльность пассажира** — как человек воспринял вашу помощь;
- **рейтинг безопасности** — соблюдение регламента и безопасность на борту.

Именно расхождение шкал и делает тренажёр не тестом. Уступка «чтобы пассажир не
жаловался» поднимает лояльность и роняет безопасность. Например, если достать
пассажирке таблетку из своей сумки, лояльность вырастет до 76, а безопасность
упадёт до 56, и сценарий будет **не сдан**: в аптечке проводника нет личных
лекарств, а последствия лежат на перевозчике.

Отдельные исходы помечены как критические (`critical_failure`) — нарушение
регламента не может быть зачтено, даже если шкалы формально держатся выше порога.

## Быстрый старт

### Docker

```bash
docker compose up --build
```

- интерфейс — http://localhost:8080
- Swagger — http://localhost:8080/docs
- API напрямую — http://localhost:8000/api/health

### Локально, без Docker

Бэкенд:

```bash
cd backend
python -m venv .venv
.venv\Scripts\pip install -r requirements-dev.txt   # Linux/macOS: .venv/bin/pip
.venv\Scripts\python -m uvicorn app.main:app --port 8000
```

Фронтенд:

```bash
cd frontend
npm install
npm run dev     # http://127.0.0.1:5173, /api проксируется на порт 8000
```

База данных создаётся сама при первом запуске: `backend/data/vsm.sqlite3`,
схема из `backend/app/schema.sql`, демо-сотрудники и достижения из
`backend/app/seed.py`. Чтобы начать с чистого листа, удалите файл базы.

### Тесты

```bash
cd backend
.venv\Scripts\python -m pytest
```

43 теста: 21 на движок сценариев (ветвление, условные переходы, шкалы, таймауты,
валидация, полнота каталога) и 22 на API (старт попытки, серверный дедлайн, разбор,
профиль, рейтинг, кабинет методиста, интеграции HR, LMS и биллинга).

## Как это устроено

```
backend/
  app/
    engine.py      чистый движок: узлы, варианты, шкалы, таймауты, разбор
    scenarios.py   загрузка и валидация JSON-сценариев
    service.py     попытка: серверные дедлайны, история шагов, запись результата
    scoring.py     опыт, уровни, достижения
    analytics.py   пробелы в компетенциях и рекомендации
    profiles.py    профиль, рейтинг, уведомления
    billing.py     доплаты на борту: повышение класса и платные услуги
    views.py       модели ответов API
    routers/       HTTP-слой
  scenarios/       сценарии в JSON — содержание отдельно от кода
  tests/
frontend/src/      React: экран ситуации, таймер, шкалы, разбор, профиль, рейтинг
docs/              архитектура, API, пользовательский путь, ограничения
```

Движок не знает ни про HTTP, ни про базу: на входе сценарий и состояние, на
выходе новое состояние и разбор. Поэтому его поведение проверяется юнит-тестами,
а на защите его можно объяснить по одному файлу.

Подробнее: [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md),
[docs/API.md](docs/API.md), [docs/USER_FLOW.md](docs/USER_FLOW.md).

## Сценарии: содержание отдельно от кода

Сценарий — это JSON в `backend/scenarios/`. Чтобы добавить развилку или изменить
цену решения, код менять не нужно:

```json
{
  "id": "check_tickets",
  "text": "«Добрый день. Позвольте Ваши билеты, я сверю вагон и место и помогу разобраться».",
  "quality": "optimal",
  "effects": { "loyalty": 5, "safety": 6, "competencies": { "conflict": 3, "regulations": 2 } },
  "debrief": "Вы признали ситуацию и сразу перешли к проверке документов, не встав ни на чью сторону.",
  "next": "s2_tickets"
}
```

Качество варианта — `optimal`, `acceptable` или `harmful`. Каждый узел ситуации
обязан содержать разные по качеству варианты, иначе выбор ничего не решает и
сценарий не будет принят.

Переход может зависеть от состояния, а не только от выбранного варианта. Условные
ветви проверяются по порядку, побеждает первая подходящая:

```json
"next": "o_good",
"branches": [
  {
    "when": { "after_harmful": true },
    "next": "o_trust_spent",
    "note": "Раньше в этой ситуации было ошибочное решение, и пассажир это помнит."
  }
]
```

В условии доступны `loyalty_below`, `loyalty_at_least`, `safety_below`,
`safety_at_least`, `after_timeout` и `after_harmful`. Шкалы проверяются уже после
применения эффектов решения, а таймауты и ошибки считаются вместе с текущим
шагом. Благодаря этому один и тот же финальный выбор приводит к разным исходам:
пройдите «Двое на одно место» по оптимальному пути и второй раз с ошибкой на
первом шаге — последняя реплика будет одна и та же, а вердикт и опыт разные.
`note` попадает в разбор шага, чтобы проводник понимал, почему ситуация
повернулась иначе.

После правки файла достаточно перечитать каталог, сервер перезапускать не нужно:

```bash
curl -X POST http://localhost:8000/api/scenarios/reload
```

Сценарии проверяются на старте и при перезагрузке: ссылка на несуществующий
узел, недостижимая ветка, узел без вариантов или таймер без исхода по таймауту
не доживут до демонстрации — сервис откажется принимать такой сценарий.

В журнале 51 ситуация из методички. У каждой несколько решений и другой финал,
если раньше в попытке уже была ошибка или молчание. Ход один: признать
ситуацию, назвать правило, предложить выход и заверить. «Двое на одно место»,
«Пассажиру стало плохо» и «Нетрезвый пассажир просит алкоголь» ветвятся ещё
подробнее.

## Данные

- В тренажёре только **синтетические данные**. Все сотрудники вымышленные и
  помечены словом «(демо)», бригады и депо тоже вымышленные.
- Персональные данные пассажиров и реальных сотрудников не собираются и не
  хранятся: в базе нет ни ФИО пассажиров, ни номеров билетов, ни контактов.
  Требования 152-ФЗ в демо-контуре выполняются тем, что персональных данных
  просто нет.
- Материалы, по которым проектировались ситуации (стандарты СТО РЖД и
  методические материалы ограниченного распространения), **в репозиторий не
  попадают**: каталог с ними исключён через `.gitignore`. В коде остались только
  собственные формулировки сценариев.

Ограничения прототипа и план развития — в
[docs/LIMITS_AND_ROADMAP.md](docs/LIMITS_AND_ROADMAP.md).

| Критерий | Баллы | Где это видно |
|---|---|---|
| Движок сценариев и механика | 0–6 | `backend/app/engine.py`, сценарии в `backend/scenarios/`, тесты `backend/tests/test_engine.py`: ветвление, условные переходы по шкалам и истории попытки, две шкалы, серверные таймауты, критические исходы |
| Самостоятельность и понимание кода | 0–6 | Содержание в JSON и один модуль движка — правка сценария и `POST /api/scenarios/reload` показываются живьём; история коммитов по шагам, тесты на каждое правило |
| Геймификация и вовлечение | 0–4 | `backend/app/scoring.py` (опыт, уровни, 6 достижений), рейтинг по бригаде/депо/компании, уведомления о челленджах и сгорающих баллах |
| Обратная связь и аналитика | 0–4 | Разбор после каждого шага и по итогам сценария, `backend/app/analytics.py`: пробелы в компетенциях и текстовые рекомендации |
| Архитектура, API, интеграция | 0–4 | Разделённые фронтенд и бэкенд, Swagger на `/docs`, заглушки HR, LMS и биллинга в `backend/app/routers/integrations.py` и `backend/app/billing.py`, запуск через `docker compose` |
| Безопасность данных | 0–3 | Только синтетика, правильные варианты не уезжают на клиент (`backend/app/views.py`), таймер считает сервер, реквизиты оплаты не принимаются и не хранятся, стандарты ограниченного распространения вне репозитория |
